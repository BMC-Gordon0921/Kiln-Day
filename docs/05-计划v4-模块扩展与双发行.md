# 计划 v4：小团队（<3 人）的模块扩展路线 + 双发行架构

先说结论，再给施工单：
1. **不要加 C#**——你想要的"网页 demo + 桌面完整版"双发行，C# 直接堵死 Web 一侧（官方文档明令 4.x 的 C# 项目不能导出 Web）。多人、图鉴、成就这些模块在 GDScript 里完全够用，它们吃的是**后端与内容**，不是语言性能。
2. **六个模块不能一起上**。按"2–3 人"的真实产能，全上 ≈ +20–30 人周，等于把项目从 6–8 周推到 6 个月以上。建议 M1 只做**图鉴 + 成就**（3 人周内、风险低、立刻提升留存），其余按依赖顺序排。
3. **"单工程双预设"是可行的**，且比"两套代码"省 70% 工作量：一份 GDScript 代码 + 两个 export preset（web=试玩、desktop=完整），用 feature tag 与内容分区控量。

## 0. 对你三个问题的直接回答

### 0.1 需要 C# 吗？——不需要，且不建议
| 事实 | 对决策的影响 |
|---|---|
| 官方：Godot 4 的 C# 项目**不能导出 Web**（[C# basics](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html)、[Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html) 两处均有警告） | 一旦选 C#，网页试玩渠道作废，与你"网页 demo + 桌面完整版"的目标直接冲突 |
| C# 需要「.NET 版 Godot + .NET 8 SDK」；本机只有 SDK 10.0.301，NuGet 走 https 被沙箱阻断 | 现在装也会卡在首次 `dotnet build`（缺 net8 targeting pack） |
| 多人用的是 Godot 高层 `MultiplayerAPI/ENet`，GDScript 一等公民 | "多人需要 C#"是误解；瓶颈在服务器与运维 |
| 本项目核心是 112×112 像素运算、窑火曲线、数值结算 | 没有需要 C# 的性能热点；真到瓶颈也优先 GDExtension(GDE)/C++ 局部替换 |

**触发改选 C# 的条件**（只列出来，不当默认）：① 放弃 Web 发行；② 团队 C# 明显强于 GDScript；③ 必须接某个 .NET 专属库。三者同时满足才值得，届时成本 ≈ 1GB 下载 + 工具链 + 放弃 Web。

### 0.2 六个模块怎么排（按"依赖 + 性价比"）
| 模块 | 依赖 | 增量工作量（2–3 人） | 建议时点 | 主要难点/风险 |
|---|---|---|---|---|
| **图鉴系统** | 数据层（必须最先） | 1.5–2.5 人周 | **M1** | 低。本质是"读资源 + 记发现标志"，还能逼你把器物数据模型洗干净 |
| **成就系统** | 事件总线 | 0.5–1 人周（Steam 成就再 +1 周） | **M1** | 低。先做本地，Steam 接入要 vendor 插件且需联网 |
| 剧情故事 | 对话运行时 + 文本量 | 1.5–3 人周 + 写作 | M2 | 中。**不要做配音/过场**；数据驱动对话 + 每站 2 个"剧情节拍"即可 |
| 角色形象 + 属性差分 | 模块化角色网格 + 平衡表 | 2–3 人周（美术占一半） | M2 | 中。属性务必**复用现有机制**（手稳→笔刷精度、耐心→窑窗容差、眼力→配色判定），否则等于再造一套平衡系统 |
| 异步多人（排行榜/云存档/幽灵回放） | 后端或文件导入 | 3–5 人周 + 每月运维 | 上线后 | 中高。**幽灵回放**最划算：把笔触序列录成数组重放，几乎零后端 |
| 实时多人/合作 | netcode + 服务器 + 反作弊 | 8–16 人周 + 长期运维 | **不建议** | 极高。<3 人团队做实时联机=项目走偏，先砍 |
| 随机开箱 | 概率表 + 合规 | 1–2 人周 | 仅"游戏币" | 合规：国内对付费随机抽取要求**公示概率**并遵守未成年人保护；海外平台另有披露要求。**建议只做游戏内货币、公示概率、加保底**，不碰真钱 |
| **双发行（web demo / desktop full）** | 工程分包 | 1–1.5 人周 | **M1** | 低。单工程双预设 + 内容分区即可 |

**硬建议：每个里程碑只允许上 1 个"大系统"**，其余为纯数值/文本增量。你现在的"窑变随机"本身就是合法随机，不需要再叠一层开箱抽卡——两者叠加会让玩家感觉被算法支配。

### 0.3 双发行怎么落地（不需要两套代码）
- 一份 `game/`，两个 export preset：`web_demo`（渲染 gl_compatibility、单线程、内容 = 1 个旅游场景 × 3 单 + 图鉴前 4 格）、`desktop_full`（同渲染器或切 Forward+，全内容）。
- 用**自定义 feature tag**（导出预设里加 `demo`）而非硬编码：`if OS.has_feature("demo")` 决定站点数量、存档是否可导出、图鉴上限。
- 内容分区：`res://content/full/` 与 `res://content/demo/`，web 预设用 include/exclude filter 排除 full 资源，**避免 demo 包里塞进完整美术**（否则包体 50MB+，加载慢、还会被扒出全内容）。
- 试玩→完整版的转化钩子：web demo 存档导出为一段"迁移码"（JSON+校验和），桌面版输入即可继承进度。成本半天，转化价值高。
- 注意：web 导出的存档是 IndexedDB，清缓存即丢；所以提示玩家"导出迁移码"。

## 7. 开发潜力评估（`docs/01` 结论）
- **技术可迁移性 9/10**：核心逻辑零引擎依赖、glTF 无贴图，资产可直接用；风险在 UI/输入重写。
- **玩法验证度 6/10**：像素捏塑→烧窑→成交闭环已可玩，但"拉坯手感"和"再来一窑"未验证；**决策门**：A1 五人测试 ≥3 人主动再来一窑；A2 无提示做出目标器型。

- **工程风险 4/10**：无导出模板、单人/小团队首次做 3D 经营、美术靠手搓 Blender。
- **六个模块的边际价值排序**（投入产出比）：图鉴 > 成就 > 双发行试玩 > 剧情 > 角色形象/属性 > 异步多人 >>>> 实时多人；开箱建议只做游戏币化变体。
- **结论**：值得做；先按策划案 v0.1 的 M1 垂直切片（单作坊 + 3 工作站）交付可玩 Demo，4 个旅游场景降为 M2 内容扩展。**"换引擎"不是价值来源，别把工期花在技术上。**
